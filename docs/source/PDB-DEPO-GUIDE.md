# PDB Deposition User Guide

The `pdb_deposition` tool generates CIF files suitable for deposition to the Protein Data Bank via PDBe.
It processes all crystals that have a `RefinementOutcome` status of `5 - Deposition ready` in SoakDB,
producing per-crystal structure CIF and structure-factor CIF files enriched with common metadata.

## Environment

You need a standard XCA environment in which to run this.
See the [User guide](USER-GUIDE.md) for details.

## Sequence and entity information

Protein sequence and entity information must be defined as described in the
[Sequence information section](USER-GUIDE.md#sequence-information) of the User Guide.

## Common metadata (`-m` / `--metadata-csv`)

You must supply a `deposition-metadata.csv` file containing information that applies to all crystals:
authors, institutions, grant details, crystal growth conditions, experimental method, etc.
Use an existing file as a starting point.

The file uses an mmcif-gen template format where each row defines one CIF field.
Columns are: category, item, headers, required, info, and one or more value columns.

### Token substitution

Several fields in the template support placeholder tokens that are expanded per-crystal at run time.
Tokens may appear in any field value, including `_struct.title` and `_struct_keywords.text`.

| Token | Replaced with |
|---|---|
| `$CompoundCode` | The compound code from SoakDB for this crystal |
| `$CrystalName` | The crystal name from SoakDB |
| `$ExternalCode2`…`$ExternalCode9` | Values from the compound-codes CSV (see below) |
| `$PoseID` | Comma-separated pose codes from the Fragalysis download CSV (see below) |

Any `$ExternalCode` token that cannot be substituted (no entry in the file, or column absent) is
removed from the output rather than left as a literal token.

### Example title template

```
_struct,title,,,,Crystal structure of Lysozyme in complex with $CompoundCode ($CrystalName) (Compound ID $ExternalCode3),,,,,,,,,,
,,,,,,,,,,,,,,,
```

### Example keywords template

```
_struct_keywords,text,,,,Diamond Light Source, I04-1, ASAP Discovery Consortium, $PoseID,,,,,,,,,,
```

## Compound codes CSV (`-c` / `--compound-codes-csv`)

An optional CSV file that supplies additional external identifiers for the `$ExternalCode` tokens.

- The **first column** must contain the crystal name.
- A **header row** must be present.
- The integer `n` in `$ExternalCoden` selects the **n-th column** (1-indexed), so `$ExternalCode3`
  takes the value from the third column.

Example:

```
CrystalName,CompoundCode,OpenBindId
Zika_NS5A-x0351,Z274555794,OB-00000142
Zika_NS5A-x0501,Z52214433,OB-00000150
Zika_NS5A-x0354,Z275165822,OB-00000163
```

## Fragalysis CSV (`-f` / `--fragalysis-csv`)

An optional CSV file downloaded from Fragalysis that provides pose codes for the `$PoseID` token.
This is the `metadata.csv` from a Fragalysis dataset download.

- **Column 1** — pose code (e.g. `A71EV2A-x0836a`)
- **Column 3** — crystal / experiment code that matches the SoakDB crystal name (e.g. `A71EV2A-x0836`)

When a crystal has more than one pose, all codes are written comma-separated:

```
A71EV2A-x0836a, A71EV2A-x0836b
```

If a crystal has no entry in this file, `$PoseID` is replaced with an empty string.

## Running pdb_deposition

```
python -m pdbdepo.pdb_deposition \
    -w <path-to-collator-output>/upload-current/upload_1 \
    -m <path-to>/deposition-metadata.csv \
    -c <path-to>/compound_codes.csv \
    -f <path-to>/fragalysis-download/metadata.csv
```

### All arguments

| Argument | Required | Description |
|---|---|---|
| `-w` / `--collator-dir` | Yes | Path to the collator output directory (the `upload_N` dir containing `config.yaml` and `meta_collator.yaml`) |
| `-m` / `--metadata-csv` | Yes | Path to the common metadata CSV used by mmcif-gen |
| `-c` / `--compound-codes-csv` | No | Path to the compound codes CSV supplying `$ExternalCode` values |
| `-f` / `--fragalysis-csv` | No | Path to the Fragalysis download `metadata.csv` supplying `$PoseID` values |
| `-d` / `--debug` | No | Copy source input files into the output directory alongside the generated CIF files |
| `--log-level` | No | Logging verbosity: `0` = INFO (default), `1` = WARN, `2` = ERROR |

## Output

All output is written to a `pdb_depo_files/` directory inside the collator output dir:

1. `pdb_depo.log` — log file for the run
2. `input<N>.cif` and `input<N>_model.cif` — the investigation CIF and the common-metadata model CIF
   generated by mmcif-gen from the metadata CSV, one pair per `model_building` input
3. `ligands.tab` — a tab-separated line per crystal, repeating
   `crystal, compound code, SMILES, InChI, InChI key` for each of that crystal's ligands
4. One subdirectory per crystal, each containing:
   - `<crystal>_struc.cif` — the 3D model CIF, ready for PDBe deposition
   - `<crystal>_sf.cif` — merged structure factors (from MTZ latest, MTZ free, and any PanDDA event maps)
   - `<crystal>_lig.cif` — a copy of the ligand restraint CIF, when SoakDB records one

An existing per-crystal subdirectory is deleted and recreated on each run, so output is never a mix of
old and new files.

When `-d` / `--debug` is specified, each crystal's subdirectory additionally gets:

- `original.cif` — the model CIF as read from the refinement output, before any editing
- `mtz_latest.cif`, `mtz_free.cif`, `event_map_<n>.cif` — the individual reflection blocks that were
  merged into `<crystal>_sf.cif`
- a copy of the data processing log file that the reflection statistics were scraped from

---

The rest of this guide describes exactly which inputs are used to produce each crystal's output files,
and how that varies with the data processing and refinement software used for that crystal.

## Which crystals are processed

Only inputs of `type: model_building` in `config.yaml` are considered; `manual` inputs are skipped
because there is no SoakDB database to read the deposition metadata from.

For each such input, the crystals are those in the SoakDB `mainTable` whose `RefinementOutcome`
begins with `5` (i.e. `5 - Deposition ready`), minus any crystal listed in that input's `exclude`
section of `config.yaml`. Note that this is deliberately narrower than the collator, which also
accepts outcomes `4` and `6` — deposition files are only produced for crystals that have been marked
as deposition ready.

Before anything is written, the sequence of every remaining crystal's model is checked against the
sequence declared for it in `config.yaml`. Any mismatch is fatal for the whole run: a wrong sequence
would be rejected by the wwPDB, so the run stops with the complete list of crystals to fix rather
than leaving partial output behind.

## Inputs used for each crystal

### From SoakDB (`mainTable`)

| Column | Used for |
|---|---|
| `CrystalName` | Identity of the crystal — names the output subdirectory and all files in it, and is the key into the compound-codes and Fragalysis CSVs |
| `CompoundCode` | The `$CompoundCode` token; a `;`-separated list is split on `;` |
| `RefinementMMCIFmodel_latest` | The Buster model (mmCIF). Its presence also **selects the refinement branch** (see below) |
| `RefinementBoundConformation` | The Refmac model (PDB), used when there is no Buster mmCIF |
| `RefinementMTZ_latest` | Reflections from the final refinement, first block of `<crystal>_sf.cif` |
| `RefinementMTZfree` | Original reflections with the free-R flag, second block of `<crystal>_sf.cif` |
| `RefinementCIF` | Ligand restraint CIF, copied out as `<crystal>_lig.cif` |
| `DataProcessingProgram` | Selects the reflection-statistics parser and the `_software` template |
| `DataProcessingPathToLogfile` | Locates the data processing statistics (see below) |

All SoakDB paths are absolute `/dls/...` paths; they are made relative and resolved against the
`base_dir` from `config.yaml`.

`RefinementMTZfree` is often recorded as a bare filename rather than a path. In that case the tool
walks up from the model's directory until it reaches the directory named after the crystal, and looks
for the file there.

### From the collator output (`meta_collator.yaml`)

| Metadata | Used for |
|---|---|
| `ligand_binding_events` | The PanDDA event map (`.ccp4`) for each modelled ligand, added as extra blocks of `<crystal>_sf.cif`. The event map's original `source_file` path is recorded in that block's `_diffrn.details` |
| `ligand_cif` → `ligands` | The compound code and SMILES for each ligand, written to `ligands.tab` (InChI and InChI key are derived from the SMILES with RDKit) |

A crystal that is in SoakDB but absent from `meta_collator.yaml` is logged as a warning and produces
no output files.

### From the model building directory

`<base_dir>/<input dir>/processing/analysis/model_building/<crystal>/`

| File | Used for |
|---|---|
| `autoprocessing/<crystal>_collection_info.cif` | Data collection information — beamline, wavelength, detector, temperature, etc. Everything in it is copied into the structure CIF, except its `_diffrn` loop which is merged with mmcif-gen's `_diffrn` data into a single row |

This file is optional: a warning is logged if it is missing and the data is simply absent from the
output.

### From the data processing directory

The directory containing the file named by `DataProcessingPathToLogfile`. Which file is used depends
on the data processing program — see [Data processing variations](#data-processing-variations).

### Common to all crystals

| Input | Used for |
|---|---|
| The metadata CSV (`-m`), via mmcif-gen | Authors, citations, grants, crystal growth, `_exptl`, `_struct`, `_struct_keywords`, `_pdbx_database_status`, polymer `_entity` rows, and the common `_refine` and `_diffrn` fields |
| `config.yaml` `sequences` (default and per-crystal variants) | The full polymer sequence written into each entity |
| The compound-codes CSV (`-c`) | `$ExternalCode2`…`$ExternalCode9` tokens for this crystal |
| The Fragalysis CSV (`-f`) | The `$PoseID` token for this crystal |
| `config/pdb-depo/*.cif` in the XCA repo | The `_software` loop rows (located via `$XCA_GIT_REPO`) |

## How `<crystal>_struc.cif` is assembled

1. **Read the model.** Either the Buster mmCIF or the Refmac PDB (see below), via gemmi, producing an
   mmCIF document. The chains are matched to the entities declared in `config.yaml` and each polymer
   entity is given its declared full sequence; entities left with no subchains are deleted.
2. **Strip what mmcif-gen owns.** The `_exptl`, `_struct`, `_struct_keywords` and
   `_pdbx_database_status` pairs and the `_exptl` and `_reflns` loops that gemmi wrote are deleted,
   because the common metadata supplies them.
3. **Merge the entities.** mmcif-gen's `_entity` rows (the polymers, with their descriptions) are
   combined with the model's non-polymer `_entity` rows (ligands, waters, ions). Tags present in only
   one of the two are filled with `?`.
4. **Merge `_refine`.** The model's refinement statistics (R-work, R-free, resolution limits, B factors)
   are concatenated with the common `_refine` fields from mmcif-gen into a single-row loop.
5. **Add the common metadata**, expanding `$CompoundCode`, `$CrystalName`, `$ExternalCodeN` and
   `$PoseID` per crystal as described above.
6. **Add the reflection statistics** scraped for this crystal's data processing program.
7. **Add the data collection information** from `<crystal>_collection_info.cif`, merging its `_diffrn`
   loop with mmcif-gen's `_diffrn` fields.
8. **Add the `_software` loop** built from the data processing and refinement templates.
9. **Tidy and check.** The `_atom_site` loop is moved to the end of the block, Diamond's internal
   beamline names are rewritten, and the document is validated (warnings only) before being written.

### Refinement variations

The refinement program is not recorded explicitly in SoakDB; it is inferred from which model file is
present:

| `RefinementMMCIFmodel_latest` | Refinement program | Model read | `_refine` in the model |
|---|---|---|---|
| Set (not `None`) | **Buster** | that mmCIF, with `gemmi.read_structure()` | pairs |
| Empty or `None` | **Refmac** | `RefinementBoundConformation` (PDB), with `gemmi.read_pdb(ignore_ter=True)` followed by `setup_entities()` | a loop |

Both forms of `_refine` end up as the same single-row loop in the output; the code handles the loop
and the pairs form separately only because the two refinement programs write them differently.

Reading the Buster mmCIF applies a workaround for a gemmi bug in which the `_refine*` categories are
silently dropped when a structure is round-tripped through gemmi's object model. All `_refine*` pairs
and loops are captured from the raw CIF beforehand and restored afterwards.

The refinement program name (`buster` or `refmac`) also selects the software template
`config/pdb-depo/buster.cif` or `config/pdb-depo/refmac.cif`. A missing template is a fatal error.

### Data processing variations

The value of `DataProcessingProgram` is lower-cased and normalised:

| SoakDB value | Normalised to |
|---|---|
| `dials` | `xia2-dials` |
| `xia2.multiplex …` (a free-text grouping suffix may follow) | `xia2-multiplex` |
| anything else, e.g. `autoproc`, `autoproc_staraniso`, `xia2-3dii` | itself, lower-cased |

The normalised name is used for two independent things: finding the reflection statistics, and
selecting the `_software` template.

**Reflection statistics** are taken from the first of these that is available:

1. `xia2.mmcif.bz2` in the same directory as the logfile. This is the preferred source — it is a
   proper mmCIF, so the `_reflns` pairs and the `_reflns_shell` loop are read straight out of its
   second block with no parsing. In practice all the xia2-based pipelines produce it.
2. The file named by `DataProcessingPathToLogfile`, parsed by `scrape_processing_stats`.
3. For `autoproc` only, when the recorded `.log` file does not exist: `aimless.log` in the same
   directory.

Where an `aimless.log` is present its AIMLESS version is scraped and logged, but it is not written
into the output — all `_software.version` values come from the templates, which leave them as `?`.

The log parsers recognise these program names and file formats:

| Program name | File parsed | Format |
|---|---|---|
| `autoproc` | `<crystal>.log` or `aimless.log` | AIMLESS text summary table |
| `autoproc_staraniso` | `staraniso_alldata-unique.table1` | STARANISO text summary table |
| `xia2-3dii` | `<crystal>.log` | xia2 text summary table |
| `xia2-dials` | `<crystal>.log` | xia2 text summary table (assumed to be the same format as `xia2-3dii`) |
| `xia2-multiplex` | the xia2.multiplex HTML report | HTML, parsed with BeautifulSoup — the "Overall" table of the combined "All data" dataset |

Each name is also recognised with underscores in place of hyphens, since `DataProcessingProgram`
values seen in the wild use both. In each case the overall values become `_reflns` and the
inner/outer shell values become a two-row `_reflns_shell` loop.

```{note}
If the log file named by `DataProcessingPathToLogfile` is missing or unparseable, and no
`xia2.mmcif.bz2` is present either, the run logs `stats could not be scraped from log file` and the
structure CIF has no `_reflns` data.
```

If `DataProcessingPathToLogfile` is empty, no statistics source is looked for at all and the
structure CIF simply has no `_reflns` data.

**The `_software` template** is `config/pdb-depo/<normalised name>.cif`. Templates exist for
`autoproc`, `autoproc_staraniso`, `xia2-3dii`, `xia2-dials` and `xia2-multiplex`. A data processing
program with no matching template — including a crystal for which SoakDB records no program at all —
is a fatal error, so adding support for a new pipeline means adding a template file named after it.

### The `_software` loop

The output `_software` loop is the data processing template's rows followed by the refinement
template's rows, renumbered so that `_software.pdbx_ordinal` runs sequentially from 1. The data
processing templates cover the whole downstream chain — data reduction and scaling, DIMPLE and REFMAC
for phasing, DIMPLE and Coot for model building, and gemmi for data extraction — so the refinement
template only needs to name the refinement program itself.

### Beamline names

ISPYB/SynchWeb records two Diamond beamlines under internal names that the wwPDB mmCIF dictionary does
not accept, so both `_diffrn_source.pdbx_synchrotron_beamline` and `_diffrn_source.type` are rewritten:

| ISPYB name | wwPDB name |
|---|---|
| `I02-1` | `VMXm` |
| `I02-2` | `VMXi` |

Every rename is logged. `I02` itself is a valid beamline and is left alone.

## How `<crystal>_sf.cif` is assembled

The structure factor file is a multi-block CIF, one block per reflection dataset:

| Block | Source | `_diffrn.details` |
|---|---|---|
| `rxxxxsf` | `RefinementMTZ_latest` | `data from final refinement with ligand <path>` |
| `rxxxxAsf` | `RefinementMTZfree` | `data from original reflections <path>` |
| `rxxxxBsf<n>` | one per PanDDA event map from `meta_collator.yaml` | `data for ligand evidence map (PanDDA event map) <source path>` |

The MTZ files are converted with gemmi's `MtzToCif`. The event maps are real-space CCP4 maps, so they
are Fourier-transformed to structure factors (`FWT`/`PHWT`) at a resolution limit of 1.5 Å first, and
the wavelength is copied over from the latest-MTZ block. A crystal with no modelled ligand simply gets
no `rxxxxBsf` blocks.

## Validation of the structure CIF

Before each `<crystal>_struc.cif` is written it is checked, and any problems are logged as
`CIF validation:` warnings. These do not stop the run — they are there to catch, before the files are
sent to the PDBe, the kinds of problem the assembly above can produce for an unusual crystal:

- a required category is missing (`_atom_site`, `_refine`, `_entity`, `_software`, `_cell`, `_symmetry`)
- a loop has duplicate tags, which is what a bad merge of model and mmcif-gen data looks like
- `_refine` numbers are missing or out of range — R-work and R-free outside 0–1, R-free below R-work,
  a high-resolution limit that is not smaller than the low-resolution limit, a negative mean B
- `_struct.title` still contains an unsubstituted `$` token
- `_atom_site` references an entity ID that `_entity` does not define
- `_software.pdbx_ordinal` is not sequential from 1
- `_diffrn_source.type` names a Diamond beamline the wwPDB dictionary does not accept
